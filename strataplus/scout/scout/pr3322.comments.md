## DFlash2 on the AMD HIP backend (RDNA4 / gfx1201) — buildable, parity-clean, measured

The `STRATA_ENABLE_DFLASH2` block refused every non-CUDA backend, so I ported it to HIP to find out whether the restriction was a code constraint or a validation gap. It is the latter: the kernels are already portable.

Branch: https://github.com/bsorensen110/Strata/tree/feat/dflash2-assistant-prefix — tip `d46a21b9`, based on `dea6920b` (v0.2.1.2) with #3356 and this PR's 56 commits cherry-picked, plus the HIP port and a merge of my not-yet-upstream RDNA4 wave.

### What the port needed — two files

1. `CMakeLists.txt`: the `FATAL_ERROR "DFlash2 currently requires the NVIDIA CUDA backend"` becomes a warning when a backend is present. `src/kernels/cuda/dflash2.cu` was already in the shared `strata_kernels` source list and compiles unchanged through `include/strata/platform/hip_compat` — only `<<<>>>`, `__syncthreads`, `__shfl_xor_sync`, `__half`/`__half2`, no tensor cores, no cuBLAS.
2. `src/kernels/dflash2_parity.cpp`: `__half_as_ushort` / `__ushort_as_half` are device-only in HIP, so the host test did not compile. Replaced with `strata::kernels::f16_from_f32` / `f32_from_f16` from `include/strata/kernels/f16_bits.hpp` (round-to-nearest-even, exact inverse — the tree's existing fp16-bits source of truth, worth using here for the CUDA build too given the note in that header).

`src/core/dflash*.cpp` needed no change: I found no CUDA-only calls in it.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DSTRATA_ENABLE_HIP=ON \
      -DSTRATA_ENABLE_CUDA=OFF -DCMAKE_HIP_ARCHITECTURES=gfx1201 -DSTRATA_ENABLE_DFLASH2=ON
cmake --build build --target strata dflash2_parity -j16
```

### Validation on gfx1201 (Radeon AI PRO R9700, ROCm nightly 10.2)

`dflash2_parity`: **PASS** — convolution, block isolation, top-k, conditioned path, confidence and nonfinite refusal. Neighbouring suites on the same build: `iq_multi_parity` 0 failures, `shared_expert_parity` 0 failures, `gr_parity --selftest` OK.

Artifact: official checkpoint at pinned `a22a1744`, `model.safetensors` sha256 verified against `d6723f2a…`, converted to Q8_0 (`776,057,536 B`, 81 tensors = 45 BF16 + 36 Q8_0, `selector_top_k 16`, taps `[5,15,25,35,45]`).

### Measurements

Target: Qwen3.8-Flash-Next IQ3_S pack, `--kv int8`, greedy, 4-token prompt, `--dflash-block 3 --dflash-window 0 --spec 8`.

Determinism first, since it changes the numbers: with `STRATA_PREFILL_CPU_SHARE=0` and `STRATA_ROUTE_TAIL_SKIP=0` set, repeated runs of the same configuration are byte-identical on this machine. Note that `--spec 2` is prompt-lookup speculation, not a target-only control, so it is not a valid "expected tokens" reference — my first cross-check used it and produced a false alarm.

Engine (`--generate`), three runs each, auto expert cache:

|---|---|---|
| MTP `--spec 4` | 52.53, 53.00 tok/s | 64.27 tok/s |
| DFlash2 Q8_0 | 58.96, 59.62 tok/s | 60.41 tok/s |

Service (`/v1/chat/completions`, 60-token prompt, 36 generated, same binary and config apart from the drafter):

| Drafter | decode | drafts accepted | text |
|---|---|---|---|
| DFlash2 Q8_0 | 110.7, 115.0, 92.9, 98.4 tok/s | 24/26, 24/26, 24/29, 23/25 | "The ocean is vast and blue." |

### Notes

- Cross-drafter token divergence I saw initially tracks expert residency, not the drafter: with a cache small enough that the CPU pool serves most experts, MTP and DFlash2 emitted identical ids for 13 tokens. - `--dflash-block 3` is the configuration setup writes and the one I measured. I did not validate `--dflash-block 0`.

--- 3chet 2026-10-24T02:10:01Z
**Build failure on gfx906 — the root cause is a macro gap, and the fix is two lines**

We hit this on v0.2.3.1 (ROCm 7.14, gfx906), and a repo-wide search for `dflash2 gfx906` returns nothing, so we may be the first:

```
src/core/dflash2.cpp:205: error: identifier "cudaStreamCreateWithPriority" is undefined
src/core/dflash2.cpp:206: error: identifier "cudaDeviceGetStreamPriorityRange" is undefined
```

**Root cause.** `STRATA_USE_HIP` is defined in exactly one place: `cmake/hip_backend.cmake:98`. That file is only included on the `STRATA_ENABLE_HIP` (wave32 / RDNA) branch. gfx906 takes the other branch — `CMakeLists.txt:76-80` sets `STRATA_ENABLE_CUDA=ON` — so it never includes `hip_backend.cmake` and never defines `STRATA_USE_HIP` anywhere. The guards at `dflash2.cpp:198` and `:446` (v0.2.3.1 line numbers) therefore evaluate false, the `#else` CUDA branch is compiled, and it references two names the gfx906 compat header doesn't map.

Upstream already knows the disconnect: `CMakeLists.txt:157-159` comments that `hip_backend.cmake` is "never included here" — the rocBLAS gating was copied without the macro.

**Why nobody reported it.** @bsorensen110's HIP port above is the best evidence: he builds with `-DSTRATA_ENABLE_HIP=ON -DSTRATA_ENABLE_CUDA=OFF` on gfx1201, so `STRATA_USE_HIP` *is* defined for him, the native branch always compiles, and his conclusion "`src/core/dflash*.cpp` needed no change: I found no CUDA-only calls in it" is correct — for his build. On gfx906 the guards evaluate false, so the CUDA branch *is* the one compiled and those calls do exist. CI doesn't run the opt-in gfx906 build either, so nothing catches it.

**Suggested fix.** Widen the two guards:

```cpp
#if defined(STRATA_USE_HIP) || defined(STRATA_HIP_GFX906)
```

This matches the idiom already used in `generate.cpp` (7 occurrences) and leaves the other 36 `STRATA_USE_HIP` sites untouched. We just rebuilt 0.1.48.1 with exactly this change: it compiles clean on gfx906, and the HIP branch is what gets built — which also restores the intended defaults (high-priority streams off, single stream) that the CUDA branch would have silently flipped on. Defining `STRATA_USE_HIP=1` for gfx906 would also work but flips 45 sites, so we avoided it.

Two caveats for whoever picks this up: on gfx906 we are still gated out at runtime by the single-card/CLI restriction at `generate.cpp:5477-5479` (`--serve`, `--batch`, or layer split all fall back to MTP), so for us this is a build-correctness fix, not a feature unlock. And the two `cuda*` → `hip*` mappings we added to `strata_hip.h` as a stopgap do compile, but they enable code paths upstream deliberately disabled on HIP — hence the guard fix instead.

Happy to test a patch.
